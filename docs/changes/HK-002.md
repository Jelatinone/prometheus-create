## 1. Outcome and acceptance

**Objective:** prove and build the two highest-risk inputs: real capture frames entering the common ingestion contract (CT-002), and a real masked photo becoming a validated mesh. **Visible flow:** given a project in `MemoryBackend` (the platform backend once merged), when a user uploads an owned chair photo, or a consenting test caller changes their FaceTime camera view, then a `SourceRegistration` and `IngestEnvelope` are produced that pass `/lab/validate` and are accepted by `ingestion.ingest`; when a mask is chosen, a `ReconstructionJob` moves queued → submitted → succeeded with its `providerRequestId` stored, and the output GLB passes `inspectGlb` with its dimensions shown on `/lab/capture`. Edge cases: duplicate and out-of-order Chert frames (`DUPLICATE`, `outOfOrder`), stale preview frames (`STALE_FRAME`), provider timeout or missing GLB (job `failed` with an error, no half-created object). **Out of scope:** persistence and HTTP ingestion (platform lane), editor UI beyond the `components/capture` panel, return video (F-012). **Cut/fallback:** PLAN CP-001 — upload-only ingestion and a labeled fixture mesh; no FaceTime or reconstruction claim without a real run. Timebox per PLAN schedule: Chert 60 min, reconstruction 30 min.

Integration seams: the Python agent validates against `lib/contracts/json-schema/ingest-envelope.schema.json`; envelopes go to the platform's `app/api/ingest` route once it exists. Masks align to the source's post-orientation pixel grid.

## 1. Outcome and acceptance

**Objective:** prove and build the two highest-risk inputs: real capture frames entering the common ingestion contract (CT-002), and a real masked photo becoming a validated mesh. **Visible flow:** given a project in `MemoryBackend` (the platform backend once merged), when a user uploads an owned chair photo, or a consenting test caller changes their FaceTime camera view, then a `SourceRegistration` and `IngestEnvelope` are produced that pass `npm run validate` and are accepted by `ingestion.ingest`; when a mask is chosen, a `ReconstructionJob` moves queued → submitted → succeeded with its `providerRequestId` stored, and the output GLB passes `inspectGlb` (`npm run validate -- glb`) with plausible dimensions. Edge cases: duplicate and out-of-order Chert frames (`DUPLICATE`, `outOfOrder`), stale preview frames (`STALE_FRAME`), provider timeout or missing GLB (job `failed` with an error, no half-created object). **Out of scope:** persistence and HTTP ingestion (platform lane), editor UI beyond the `components/capture` panel, return video (F-012). **Cut/fallback:** PLAN CP-001 — upload-only ingestion and a labeled fixture mesh; no FaceTime or reconstruction claim without a real run. Timebox per PLAN schedule: Chert 60 min, reconstruction 30 min.

Integration seams: the Python agent validates against `lib/contracts/json-schema/ingest-envelope.schema.json`; envelopes go to the platform's `app/api/ingest` route once it exists. Masks align to the source's post-orientation pixel grid.

**Delivered behavior (offline and browser-verified):**

- **Capture (`lib/capture`).** Photos (PNG, JPEG, WebP) are identified by their bytes, not the file name or browser-reported type. EXIF rotation is applied: a real browser re-encodes an orientation-6 JPEG upright, and the original stays the source asset. Every stored frame carries a `sha256:` hash. The same `CaptureIngestor` path handles uploads, phone photos and live phone-camera frames, and uploaded clips (MP4, MOV, WebM) with chosen frames. It goes through `putAsset`, then `registerSource`, then `ingest` on `MemoryBackend`. Asset IDs are derived from the project, asset kind and content, so a retried upload reuses its asset.
- **Reconstruction (`lib/reconstruction`).** `runReconstruction` drives a `ReconstructionJob` from queued to submitted (with `providerRequestId` stored before the first poll), then running, then succeeded or failed, through `JobStore`.
  - Each GLB is checked with `inspectGlb` and normalized: a wrapper root node applies the unit scale, the +Z→+Y conversion and bottom-centre recentring, leaving the binary data untouched. `Geometry.normalization` is recorded.
  - Output copies go to owned storage, and `canApplyJobResult` decides whether the result may be applied.
  - `resumeReconstruction` polls the stored request ID and never resubmits. `runSegmentation` (`fal-ai/sam-3/image`) produces masks aligned to the frame.
  - A live CLI (`lib/reconstruction/live-run.ts`) is ready to run once a key exists.
- **Capture agent (`services/capture-agent`, Python).** It builds envelopes and source registrations and validates them against the generated JSON Schema, plus the Chert rules JSON Schema cannot express. It also covers upright JPEG frames, frame selection (first frame, changed view, a periodic anchor, rate-limited previews) with monotonic sequencing, and CT-005 session snapshots. An outbox is replayed through the gateway by `lib/capture/replay-outbox.ts`. The Chert Calls API client and the LiveKit caller-video runner (`python -m capture_agent.live check|call`) are written but **not yet run against Chert**.
- **Panel (`components/capture`).** `CapturePanel` has Upload, Phone camera, Video and FaceTime tabs and uses the ADR-002 tokens. It shows result IDs and contract error codes. FaceTime is honestly disabled. A development-only harness at `/api/capture/lab` returns 404 in production builds.

## 1. Outcome and acceptance

**Objective:** the editor shows a reconstructed object as a mesh or an inferred splat under one shared transform. One Generate action makes 2–3 objects. A persistent timeline drives what PNG (and later video) exports.

**Visible flow:** given an object whose `SceneObject.splat` references an S1 splat asset, when the user switches the layer to Splat and moves, rotates and scales the object, then the splat moves exactly with the mesh. It survives undo, fork and save/reload. Switching back to Mesh shows the same pose.

**Edge cases:** a missing or invalid splat falls back to the mesh with a notice. Scrubbing or switching layers never calls a provider. A Generate batch with one failed child keeps the others and retries only that child, without resubmitting a job that has a provider request ID.

**Out of scope:** splat persistence and provider work (Track A), shared contract changes without Cody's approval, remote video streaming, physics.

**Cut/fallback:** per checkpoint record in PLAN §5.

Checkpoint acceptance gates are the `acceptance_gate` fields of CP-011 to CP-015 in PLAN §5. Seams S1 (splat asset form: 3DGS PLY already in the mesh's object-local space, so the editor applies **no** extra normalization), S2 (`outcome.splatAsset`), S3 (attach in `lib/editor/reconstruction.ts`) and S4 phase 1 (child jobs on the existing single-mask API) are defined in PLAN §1 "Current continuation v4".

## 3. Actual changes and evidence

Record each checkpoint as `### CP-01N evidence`: delivered behaviour, the revision, the verification table (gate rows must pass), screenshots for browser checks, and limitations.

### CP-011 evidence

**Delivered behavior:**
- **Layer section in the inspector.** Every selected object has a Layer section.
  - **Attach splat / Replace splat** takes a local `.ply`. The file is checked in the browser as an S1 3DGS PLY (binary little-endian, all 14 required properties, a body as long as declared). It is then uploaded through the existing private signed-upload path as a `splat` asset and attached as `SceneObject.splat = { assetId, enabled: true, validForGeometryRevision: <current> }`.
  - The **Mesh | Splat** switch writes `splat.enabled` as one undoable manifest edit, so it saves and forks like any other edit.
- **Viewport layers.** Each object's group has a `mesh` layer and a `splat` layer under the one object transform; no extra normalization is applied (S1). Spark is loaded with a dynamic `import()` the first time a splat is needed, so SSR never evaluates it. GLB export carries only the mesh layer; PNG export draws whichever layer is showing.
- **Fallbacks.**
  - A file that fails the check is rejected before upload, with a notice; the mesh stays.
  - An attached splat that cannot be downloaded or fails the check at load shows the mesh, with a notice and an inline reason in the inspector.
  - A splat made for an older `geometryRevision` is "stale": the Splat button is disabled and the mesh is shown.
- **S3 attach.** `attachedSplat()` in `lib/editor/reconstruction.ts` reads `outcome.splatAsset` structurally until Track A's S2 field lands. It sets `{ assetId, enabled: false, validForGeometryRevision }` only for a `splat`-kind asset from the same project; otherwise the object stays mesh-only. `reconstructedObject()` now uses it.
- **Spark:** `@sparkjsdev/spark` **2.4.0** (exact; published 2026-10-20; MIT; no dependencies). Its peer range `three >=0.180.0` includes the pinned 0.187.0. It inlines its sort worker as a blob/data URL, so no bundler or worker configuration was needed. Installed docs read: `node_modules/@sparkjsdev/spark/README.md` and `dist/types/SplatMesh.d.ts` (`fileBytes`, `fileName`, `initialized`, `SparkRenderer({ renderer })`). The lockfile change was merged by hand (a 13-line diff); npm/cli#4828 prunes the rolldown Windows binding on `npm install`, so I ran `npm ci` afterwards to confirm the binding.
